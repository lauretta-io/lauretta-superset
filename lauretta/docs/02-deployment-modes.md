# 02 Deployment modes

**For:** anyone starting a stack.

This repo supports three ways of running Superset. They share one Dockerfile and one
Superset config; each mode layers on top of the last rather than forking it.

| Mode | Compose file | Use for | Access |
|---|---|---|---|
| 1. **dev** | `docker-compose.yml` | Local development, hot reload, Cypress | `http://localhost:9000` |
| 2. **nondev** | `docker-compose-non-dev.yml` | Locally hosted, plain HTTP, trusted network | `http://<host>:8088` |
| 3. **secure** | `docker-compose-secure.yml` | Internet-facing, must pass security scans. **Set up via [06](06-secure-mode.md).** | `https://<domain>` via host nginx |

> Modes 1 and 2 are plain HTTP with development defaults, run as root, and log in as
> `admin`/`admin` unless `ADMIN_PASSWORD` is set in `docker/.env-local`. Do not expose
> either to an untrusted network.

Modes are mutually exclusive on one host: they all want port 8088. Stop one before
starting another. Every `docker compose` command in these docs passes `-f`
explicitly — without it, Compose uses `docker-compose.yml`, which is the **dev**
stack whichever one you meant.

## Before any mode: dashboards

Every mode runs the Lauretta dashboard import on start, which reads
`lauretta/dashboards/config.json`. Without it the stack starts with no dashboards.

```bash
cp lauretta/dashboards/config.example.json lauretta/dashboards/config.json
chmod 600 lauretta/dashboards/config.json
$EDITOR lauretta/dashboards/config.json   # see 04-dashboards-and-floor-maps.md
```

## Mode 1 — dev

```bash
docker compose up
```

Frontend is served by a webpack dev server and rebuilds on change. Uses the `dev`
image stage and runs as `root`.

**Use `http://localhost:9000`, not `:8088`.** This is the one mode where the two are
not interchangeable. `DEV_MODE=true` skips `npm run build`, so the image ships an
empty `/app/superset/static/assets` and the app on `:8088` serves HTML whose every
asset 404s — an unstyled page with a broken favicon, while `/health` and the REST API
still answer 200. The webpack dev server on `:9000` serves the assets it has just
built *and* proxies everything else to the app (`superset-frontend/webpack.proxy-config.js`,
pointed at the backend by the `superset` environment variable in `docker-compose.yml`),
so it is the only port that gives you a complete UI.

`http://localhost` (port 80) also works: the compose nginx sends `/static` to `:9000`
and everything else to `:8088`, reassembling the same thing from the other direction.
`:9000` is the one to use — it is where hot module reloading is wired up.

Both are published on loopback only.

## Mode 2 — nondev

```bash
docker compose -f docker-compose-non-dev.yml up -d --build
```

Gunicorn instead of the Flask dev server, frontend bundle baked into the image.
Still uses the `dev` image stage and runs as `root`. Port 8088 is published on all
interfaces, so other hosts on the network can reach it.

Pass `--build` the first time, and after any frontend change — this mode serves
`/static` from the image, so the bundle has to exist in it.

## Mode 3 — secure

> **Read [06 Secure mode](06-secure-mode.md) before starting a secure instance.**
> Some steps only take effect if they are done before the first start — the admin
> password, for one, is fixed when the `admin` user is created — and a stack started
> without them either fails to start or has to be corrected by hand afterwards.

Non-root containers, HTTPS through an nginx reverse proxy on the host, authenticated
Redis, and secrets in a gitignored `docker/.env-secure` generated by
`scripts/generate-secure-secrets.sh`. Setup also covers file ownership for floor-map
uploads, installing the reverse proxy and its certificate, and the first login.

## After starting

```bash
docker compose -f <compose-file> logs -f superset-init   # migrations, then the dashboard import
```

`superset-init` exits when it is done; the app container waits for it. Then open the
address from the table above. If the page renders unstyled, see "The stack itself" in
[09](09-verification-and-troubleshooting.md).

Each mode keeps its own data. Modes 1 and 2 share the `lauretta-superset` compose
project and so share volumes; mode 3 uses `lauretta-superset-secure` and starts empty.
To move dashboards across, see "Migrating between modes" in
[07 Operations](07-operations.md).
